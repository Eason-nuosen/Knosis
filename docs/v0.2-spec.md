## 0. 核心原则：简洁、清晰、灵活的开源工程代码

**这是本项目最重要的要求，优先级高于本文其他任何细节。** 目标是一个别人愿意读、愿意改、愿意贡献的开源项目，而不是一个「什么情况都兜住」的系统。

**要做：**

- 每个模块短小、职责单一；函数名和参数一看就懂。优先写 30 行能读完的函数，而不是 100 行的「完备」实现。
- 用最直接的写法：标准库与已有依赖能做的，不引入新依赖、不造抽象层。
- 灵活：路径、参数都可以由调用方传入；默认值合理，但不把行为写死。
- 与现有代码风格一致（参考 `knosis/dataset.py`、`knosis/benchmarks/*.py`：每个 loader 40–70 行）。
- 注释只写代码本身表达不了的约束（比如「这里必须删掉 clean 图没有的属性，否则泄漏答案」），不写「这行在做什么」。中文注释与文档。

**不要做：**

- 不写防御性代码：不做版本探测、不做输入合法性校验层、不包 try/except 去吞错误或兜底；出错就让它直接抛出，错误信息由 Python 自己给。
- 不写冗余代码：不为「以后可能需要」预留参数、配置项、抽象基类、插件机制；本版用不到的就不写。
- 不重复：同一件事只在一处实现（例如知识单元的检查只在 `knowledge.py`）。
- 不过度设计：不要 Manager / Factory / Registry 套 Registry；一个 dict 能解决的不写类。
- 不写大段日志、进度条、彩色输出；需要时 `print` 一行即可。

**自检**：每完成一步，回头看一遍新增代码 —— 能删的删掉，能合并的合并，一个函数能说清的不要拆成三个。行数越少越好，前提是清晰。

## 0.1 其他约定

- **现有结构不动**：`knosis/dataset.py`（`Dataset` / `Task` / `Unit` / `read`）、`knosis/benchmarks/*`（loader）、`knosis/cards/*`、`knosis/download.py`、`knosis/cli.py` 已有，在其上扩展。
- **环境**：本机 conda 环境 `knosis`，Python 在 `/Users/eason/miniconda3/envs/knosis/bin/python`；代码里不要写死这个路径（工作区记录 `sys.executable`，工具用环境变量指定，见 6.2），部分工具会在 Linux GPU 服务器上运行。
  **不要用 `conda run`**（在这台机器上会无限卡住），一律直接调用环境里的 `bin/python` / `bin/pip`。
- **测试**：`tests/` 下用 pytest；每一步完成都要 `python -m pytest -q` 全绿。不需要真实数据的测试用 `tmp_path` 造最小数据；需要真实数据的测试在数据不存在时 `pytest.skip`。
- **数据目录**：原始基准数据在 `data/<benchmark>/`（`knosis.data_dir(name)`）。工作区默认建在 `ws/` 下，把 `ws/` 加进 `.gitignore`。

## 2. 步骤 1：知识单元格式与结构检查（`knosis/knowledge.py`）

### 2.1 格式

`knowledge/units.jsonl`，一行一个 JSON 对象：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 工作区内唯一，字符串 |
| `content` | 是 | 知识内容（自然语言 / 公式 / 三元组文本） |
| `form` | 是 | `finding` / `fact` / `rule` / `formula` / `schema` / `tool` |
| `provenance` | 是 | 来源，写法见 2.2 |
| `status` | 是 | `observed` / `inferred` / `verified` / `retracted` / `stale` |
| `condition` | 否 | 适用条件与已知例外 |
| `derived_from` | 否 | 派生自哪些单元的 id 列表 |
| `support` | 否 | 独立支持数（整数） |
| `meta` | 否 | 任意附加信息（支持样本数、反例数、工具分数等） |

### 2.2 `provenance` 写法

- 数据：`data/<文件>#<定位>`
  - 图节点 `data/graph.gpickle#node/<节点id>`
  - 图边 `data/graph.gpickle#edge/<src>|<label>|<dst>`
  - 表行 `data/train.parquet#row/<row_id>`；表列 `data/train.parquet#col/<列名>`
- 工具：`tool:<name>@<version>(<k=v,...>)`
- 纯由其他单元推出：`derived`（此时 `derived_from` 必须非空）
- 多个来源用 ` ; ` 连接。

### 2.3 接口

```python
def load_units(path) -> list[dict]
def write_units(path, units: list[dict]) -> None
def check_units(units, known_ids=frozenset(), root: Path | None = None) -> list[str]   # 返回问题清单，空=通过
```

`check_units` 的规则（只查结构，不判断内容对错）：

1. 必填字段齐全且非空；`id` 不重复；`status`、`form` 取值合法。
2. `provenance` 以 `data/` 开头时，`#` 前的文件必须在 `root` 下存在。
3. **I1**：`derived_from` 里每个 id 必须存在于本文件或 `known_ids`（历史版本里出现过的 id）。`provenance == "derived"` 时 `derived_from` 不能为空。
4. **I5**：若某单元的 `derived_from` 包含 `status == "retracted"` 的单元，则它的 `status` 必须是 `retracted` 或 `stale`。

### 2.4 验收

`tests/test_knowledge.py`：各规则各一个正例一个反例。

## 3. 步骤 2：导出器与 BRIEF（`knosis/workspace/export.py`）

每个基准一个函数 `export_<name>(ds: Dataset, ws: Path, **opts) -> dict`，把 agent 可见的数据写进 `ws/data/`，并返回：

```python
{
  "brief": str,          # BRIEF.md 全文
  "tasks": list[dict],   # decide 阶段的题目，每个 {"id", "kind", "question", ...}，绝不含答案
  "holdout": list[str],  # 出现在 BRIEF 示例里的题目 id（从 tasks 中剔除，评测时排除）
  "output": str,         # decide 阶段的交付文件名
}
```

`EXPORTERS = {"ngdbench": export_ngdbench, "tabarena": export_tabarena}`。其他基准本版不支持。

**导出必须是确定性的**（同样输入得到同样的 `tasks`），因为 decide 阶段会重新调用导出器取题（见 4.3）。

### 3.1 NGDBench（`export_ngdbench`）

1. 读 perturbed 图（`ds.read("perturbed")`；没有 perturbed 的域读 clean）。
2. **去掉加噪痕迹（关键）**：perturbed 图里带着泄漏答案的属性 —— 边上 `is_noise` / `noise_similarity` / `relation`，节点上 `noise_similarity` / `original_name`。规则：读 clean 图，收集 clean 图里出现过的节点属性键与边属性键，**perturbed 图里不在这两个集合里的属性键全部删除**（不要硬编码字段名）。
3. 写 `ws/data/graph.gpickle`（`pickle.dump`）。**不复制** `noise_info/`、clean 图、查询文件。
4. 题目：`ds.tasks` 中 `kind` 以 `complex_query` 或 `query_results` 开头的（本版不含 management 类）。每题导出 `{"id", "kind", "question": meta["nlp"] 或 input, "cypher": meta["query"]}`。**不导出** `answer`、`noise_answer`、`same_as_cleangraph`。
5. 示例题：从题目中等间隔取 6 道作为 BRIEF 示例，记入 `holdout`，并从 `tasks` 中剔除。
6. BRIEF：读 `briefs/ngdbench-<scenario>.md`，用 `string.Template.safe_substitute(examples=...)` 填入示例（每行 `- [kind] question`）。没有对应 BRIEF 的域直接报错即可。
7. `output = "predictions.jsonl"`（每行 `{"id": 题目id, "answer": ...}`）。

### 3.2 TabArena（`export_tabarena`，参数 `repeat=0, fold=0`）

1. 取 `ds.tasks` 中 `meta["repeat"] == repeat and meta["fold"] == fold` 的划分。
2. `ws/data/train.parquet`：训练行，含目标列，加 `row_id` 列（原始行号）。
3. `ws/data/test_features.parquet`：测试行，**删掉目标列**，加 `row_id`。
4. BRIEF：读 `briefs/tabarena.md` 模板，填 `name / target / problem_type / n_train / n_test / n_features / columns / description`。`columns` 每行 `` - `列名`：dtype（类别）  ← 目标 ``；`description` 取 `ds.schema["description"]` 前 3000 字符。
5. `tasks = [{"id": task.id, "kind": problem_type, "question": "为 data/test_features.parquet 的每一行预测 `<target>`。"}]`，`holdout = []`。
6. `output = "predictions.csv"`（列 `row_id, prediction`；分类可额外给各类概率列）。

### 3.3 BRIEF 内容

两个文件结构相同，三节：**数据是什么 / 下游任务是什么 / 知识应该服务什么**。

- `briefs/ngdbench-ngd-fin.md`：手写。事实（来自对 NGD-Fin 图的统计，实现者可复核）：
  - `MultiDiGraph`，10865 节点、60476 边（观测图）；节点 id 形如 `Account:9570149208163490`，类型在节点属性 `label`，边类型在边属性 `label`。
  - 节点类型与数量：Account 3997、Loan 2445、Company 1782、Medium 1752、Person 889；少数节点本来就没有 `label`（clean 图里也如此），不一定是噪声。
  - 主要属性：Account（accountType、balance、accountLevel、isBlocked、createTime、lastLoginTime、nickname、email、phonenum）；Loan（loanAmount、balance、interestRate、loanUsage、createTime）；Company（companyName、business、city、country、description、url、isBlocked）；Medium（mediumType、riskLevel、isBlocked、lastLoginTime）；Person（personName、gender、birthday、city、country、isBlocked）。
  - 边类型与数量：Account_Withdraw_Account 17211、Account_Transfer_Account 13883、Medium_SignIn_Account 5512、Loan_Deposit_Account 5082、Account_Repay_Loan 3936、Company_Invest_Company 2726、Person_Invest_Company 2635、Person_Own_Account 2248、Company_Own_Account 2230、Company_Apply_Loan 1534、Person_Apply_Loan 1481、Company_Guarantee_Company 1048、Person_Guarantee_Person 950。
  - 说明这是含噪声的观测图（可能有虚假边、缺失边、连错的边、被改坏的属性），**不要写噪声的数量或比例**。
  - 下游任务：非聚合（多跳查找）与聚合（计数 / 求和 / 平均 / 比较）两类问答，每题有 NL 问题与 Cypher；答案以真实图为准；然后放 `$examples`。
  - 知识应该服务什么：可疑的边 / 节点 / 属性及理由；稳定的结构规律（类型约束、度与数值范围、时间先后）；常被查询的统计量去噪前后的变化。
- `briefs/tabarena.md`：模板（占位符见 3.2），第三节写：数据质量问题（缺失、异常、重复、可疑取值、潜在泄漏特征）、特征与目标的规律及其条件与例外、可用领域知识解释的结构。

### 3.4 验收（`tests/test_workspace.py` 的导出部分）

- 造一个最小的 clean / perturbed 图（perturbed 边带 `is_noise`、节点带 `original_name`），导出后 `graph.gpickle` 里**不存在** clean 图没有的属性键。
- 导出的 `tasks` 里没有 `answer` / `noise_answer` / `same_as_cleangraph` 字段；`holdout` 的 id 不在 `tasks` 里。
- TabArena：`test_features.parquet` 不含目标列；train / test 的 `row_id` 与划分一致。
- 真实数据（存在时）：`ngd-fin` 导出后，图的边属性键集合 == `{"label"}`。

## 4. 步骤 3：工作区（`knosis/workspace/__init__.py`）

### 4.1 目录

```
ws/<benchmark>-<scenario>/        （git 仓库）
├── BRIEF.md
├── AGENTS.md                     从 workspace/AGENTS.md 渲染
├── CLAUDE.md                     内容只有一行：@AGENTS.md
├── TOOLS.md                      步骤 5 生成；本步骤先写占位「（暂无工具）」
├── data/                         导出的可见数据
├── tasks/                        decide 阶段才写入 tasks.jsonl
├── stages/1_explore/  2_extract/  3_refine/  4_decide/
├── knowledge/units.jsonl         当前知识层（init 时为空文件）
└── .knosis/state.json
```

`state.json`：

```json
{"benchmark": "ngdbench", "scenario": "ngd-fin", "options": {},
 "stage": "explore", "round": 1, "holdout": [...], "output": "predictions.jsonl",
 "python": "/Users/eason/miniconda3/envs/knosis/bin/python", "created": "<iso时间>"}
```

**题目不存进工作区**（`.knosis/` 也是 agent 能读到的）；decide 阶段由导出器重新生成（导出是确定性的）。

### 4.2 函数与 CLI

```python
def init(benchmark, scenario, out=None, **options) -> Path
def next_prompt(ws) -> str          # 当前阶段的完整指令；进入 decide 时顺带写 tasks/tasks.jsonl
def check(ws) -> list[str]          # 验收当前阶段；通过则提交 git 并推进状态；返回问题清单
def goto(ws, stage) -> None         # 手动切换阶段（如 refine 跑够轮数后切到 decide）
def status(ws) -> dict
def fork(ws, out, knowledge="K_final") -> Path   # 为对照实验复制工作区并替换知识层
def run(ws, agent="codex", stages=None, rounds=1) -> None   # 驱动模式，见 4.6
```

CLI（加到 `knosis/cli.py`）：

```
knosis ws init <benchmark> <scenario> [--out DIR] [--repeat 0 --fold 0]
knosis ws next [DIR]          # 默认当前目录
knosis ws check [DIR]
knosis ws goto [DIR] <stage>
knosis ws status [DIR]
knosis ws fork <DIR> --out <DIR2> --knowledge none|K_0|K_<n>|K_final
knosis ws run <DIR> --agent codex|claude [--stage S ...] [--rounds N]
```

### 4.3 各函数行为

- **init**：`load_dataset(benchmark, scenario)` → `EXPORTERS[benchmark](ds, ws, **options)` → 写 BRIEF / AGENTS / CLAUDE / TOOLS / 空 `knowledge/units.jsonl` / 各 stages 目录 / `state.json` → `git init` + 提交「init」。`out` 默认 `ws/<benchmark>-<scenario>`。
- **next_prompt**：读 `workspace/stages/<stage>.md`，用 `string.Template` 填 `round`、`output`、`python`。阶段为 `decide` 且 `tasks/tasks.jsonl` 不存在时，重新调用导出器拿 `tasks` 写入（导出器的数据写出可跳过 —— 给导出器加 `write_data=False` 参数，或拆成两个函数，二选一，保持简单）。
- **check**（按当前阶段）：
  - `explore`：`stages/1_explore/notes.md` 存在且非空；`units.jsonl` 通过 `check_units`（可以为空）。
  - `extract`：`units.jsonl` 非空且通过检查；通过后复制到 `stages/2_extract/units.jsonl`（即 `K_0`）；推进到 `refine`。
  - `refine`：`stages/3_refine/round_<n>/changelog.md` 存在；`units.jsonl` 通过检查；复制到 `round_<n>/units.jsonl`（即 `K_n`）；`round += 1`，**停留在 refine**（用 `goto decide` 离开）。
  - `decide`：`stages/4_decide/<output>` 存在；`predictions.jsonl` 时每行 `id` 都在 `tasks/tasks.jsonl` 里。
  - `known_ids` = 所有历史快照（`stages/**/units.jsonl`）里的 id；`root` = 工作区目录。
  - 通过：`git add -A && git commit -m "<stage>[ round n]: <单元数> units"`，推进阶段（explore→extract→refine→…）。不通过：打印问题清单，不提交，退出码 1。
- **fork**：复制整个工作区（含 `.git`）到 `out`；`knowledge/units.jsonl` 换成指定版本（`none` = 空文件，`K_0` = `stages/2_extract/units.jsonl`，`K_<n>` = 第 n 轮快照，`K_final` = 当前）；`none` 时同时删掉 `stages/` 下的所有快照与笔记；状态设为 `decide`；提交「fork: knowledge=…」。

### 4.4 `workspace/AGENTS.md`（渲染进工作区，占位 `$python`）

内容要点（实现者据此写成正文，保持一页以内）：

1. 这是一个 Knosis 工作区：先读 `BRIEF.md`；当前阶段的目标用 `knosis ws next .` 查看；完成后 `knosis ws check .`。
2. 目录约定（4.1 的表）；**不要修改 `data/`**；代码与笔记写在当前阶段的 `stages/` 子目录；知识写在 `knowledge/units.jsonl`。
3. 知识单元格式（2.1 的表）与 `provenance` 写法（2.2）。
4. Python 用 `$python`（已装 pandas / pyarrow / networkx 等）。可用的工具见 `TOOLS.md`，通过 `knosis tool run <name> ...` 调用；工具输出一律是 `inferred`，需要自己判断与验证。
5. 不要试图寻找或读取答案；工作区之外的文件与本任务无关。

### 4.5 阶段模板（`workspace/stages/*.md`）

每份固定四节：**目标 / 输入 / 交付物 / 验收标准**，只写目标不写步骤。

- **explore.md**
  - 目标：读懂数据的结构、分布与质量问题，重点找出可疑数据（噪声、异常、不一致、缺失）并说明依据；不需要现在得出规律。
  - 输入：`BRIEF.md`、`data/`。
  - 交付物：`stages/1_explore/notes.md`（看了什么、发现了什么、哪些不确定）；每个可疑项写成 `form=finding`、`status=inferred` 的知识单元；分析代码放 `stages/1_explore/`。
  - 验收：`provenance` 指向 `data/` 的具体位置；可疑项要有依据（统计量 / 违反的约束 / 矛盾）；完成后 `knosis ws check .`。
- **extract.md**
  - 目标：提取对下游任务有用、能复用的知识（事实 / 规则 / 模式 / 方程 / schema 约束），写清成立条件；**不要把具体题目的答案存成知识**。
  - 输入：`BRIEF.md`、`data/`、`stages/1_explore/notes.md`、已有的 finding。
  - 交付物：在 `knowledge/units.jsonl` 里追加（可修改或撤回已有单元）；代码放 `stages/2_extract/`。
  - 验收：每条写 `condition`；规则与方程须在数据上验证，在 `meta` 里报告支持数与反例数，验证过的用 `verified`；派生的写 `derived_from`。
- **refine.md**（占位 `$round`）
  - 目标：改进知识层（第 `$round` 轮）：合并重复、把实例概括成带条件与例外的规则、用数据重新验证、修复冲突、撤回不成立的（`retracted`），并把受影响的派生单元标为 `stale`。
  - 输入：当前 `knowledge/units.jsonl`、`data/`、前几轮的 changelog。
  - 交付物：更新后的 `knowledge/units.jsonl`；`stages/3_refine/round_$round/changelog.md`（改了什么、为什么、验证结果）。
  - 验收：结构检查通过（I1 / I5）；撤回与合并不得丢失来源（新单元的 `derived_from` 指向被合并的单元）。
- **decide.md**（占位 `$output`）
  - 目标：用 `knowledge/units.jsonl` 中的知识完成 `tasks/tasks.jsonl` 里的任务。
  - 输入：`tasks/tasks.jsonl`、`knowledge/units.jsonl`、`data/`。
  - 交付物：`stages/4_decide/$output`；可选 `stages/4_decide/used_units.jsonl`（每题用到了哪些单元 id）。
  - 验收：每道题都有输出。

### 4.6 驱动模式 `run`

循环：`next_prompt` → 启动 agent → `check` → 记录日志 `stages/<stage>/agent.log`。不通过时把问题清单附在 prompt 后再跑一次（最多 2 次），仍不通过就停下报错。`--stage` 指定要跑的阶段（默认 explore、extract）；refine 按 `--rounds` 跑 N 轮后自动 `goto decide`。

启动命令（已在本机核实：codex-cli 0.160.0、Claude Code 2.1.289）：

- Codex：`codex exec -C <ws> --sandbox workspace-write --skip-git-repo-check "<prompt>"`
- Claude Code：在 `cwd=<ws>` 下 `claude -p "<prompt>" --permission-mode acceptEdits --allowedTools "Bash Read Edit Write"`（`--permission-mode` 与 `--allowedTools` 的确切取值请用 `claude --help` 再核实一次）

嵌套控制：启动子进程时设环境变量 `KNOSIS_DEPTH = 当前值 + 1`；`run` 发现 `KNOSIS_DEPTH >= 1` 时直接报错（不允许 agent 里再驱动 agent）。

### 4.7 验收

- `test_workspace.py`：用 `tmp_path` 下的 TabArena 假数据（参考现有 `tests/test_loaders.py::test_tabarena`）走一遍 `init → next → check(失败) → 写 notes.md → check(通过, stage=extract) → 写 units → check(通过, stage=refine, 有 K_0 快照) → goto decide → next 写出 tasks.jsonl → fork(knowledge=none)`；检查 git 提交数与 `state.json`。
- 手动：`knosis ws init ngdbench ngd-fin` 与 `knosis ws init tabarena houses` 在真实数据上成功；`ws/ngdbench-ngd-fin/` 里没有 `noise_info`、没有 clean 图、没有题目文件。

## 6. 步骤 5：工具中心框架（`knosis/tools/__init__.py`）

### 6.1 工具的组成

每个工具一个目录 `knosis/tools/<name>/`：

- `TOOL.md`：frontmatter + 说明。frontmatter 字段：
  ```yaml
  name: ultra
  version: "0.1"
  kind: model            # model | llm | skill
  modality: [graph]      # graph | table | text | timeseries
  stage: [explore, extract]
  env: knosis-ultra      # 建议的专用环境名，仅作说明
  license: "..."         # 代码与模型权重的许可，必填
  ```
  正文：用途、输入、输出、参数、局限。
- `run.py`：命令行入口，用 argparse；只读输入、写到 `--out` 指定的目录，**不修改输入数据**。

### 6.2 运行器与 CLI

```python
def list_tools(modality=None) -> list[dict]       # 解析各 TOOL.md 的 frontmatter
def run_tool(name, args: list[str]) -> int         # subprocess: [<python>, <tool_dir>/run.py, *args]
```

```
knosis tool list [--modality graph]
knosis tool card <name>
knosis tool run <name> -- <工具自己的参数>
```

frontmatter 用 `yaml.safe_load` 解析（取第一对 `---` 之间的内容）。

工具用哪个 Python：环境变量 `KNOSIS_<NAME>_PYTHON`（如 `KNOSIS_ULTRA_PYTHON=/opt/conda/envs/knosis-ultra/bin/python`），没设就用当前解释器。机器不同（本机 / 服务器）只改环境变量，不改代码。**直接调用解释器路径，不用 `conda run`**。

### 6.3 输出约定（所有工具一致）

在 `--out` 目录写：

1. 工具自己的结果表（parquet），如每条边的分数；
2. `units.jsonl`：把值得注意的结果写成知识单元，`provenance = tool:<name>@<version>(<参数>) ; <数据定位>`，`status = inferred`，分数放 `meta.score`；
3. `run.json`：工具名、版本、参数、耗时、输入文件路径。

工具**不**直接写 `knowledge/units.jsonl`；由 agent 决定采纳哪些。

### 6.4 TOOLS.md 生成

`workspace.init` 时按数据形态（ngdbench → graph，tabarena → table）筛选 `list_tools`，写出工作区的 `TOOLS.md`：每个工具一节（名称、用途、调用示例、输出位置、许可）。

### 6.5 验收

`test_tools.py`：在 `tmp_path` 下造一个假工具（TOOL.md + 打印参数的 run.py，`python` 用当前解释器），测 `list_tools` 的筛选与 `run_tool` 的调用。

## 7. 步骤 6：ULTRA 工具（`tools/ultra`）

ULTRA（Galkin et al., ICLR 2024，https://github.com/DeepGraphLearning/ULTRA）：KG 基础模型，零样本对任意关系词表做链接预测，仓库自带预训练 checkpoint。

**本版只实现代码与简单的 smoke test，实际运行放在有 GPU 的 Linux 服务器上。** 不需要在本机（Mac）跑通，也不需要评估效果。

1. `TOOL.md`：写清依赖（按 ULTRA README 的 torch / PyG 版本）、checkpoint 的获取方式、`--device`（默认有 GPU 用 `cuda`，否则 `cpu`）、代码与权重的许可。
2. `run.py`：
   - 输入 `--graph data/graph.gpickle --out <dir> [--ckpt PATH] [--topk 50] [--max-edges N] [--device cuda]`。
   - 把 NetworkX 图转成 ULTRA 需要的三元组（节点 → 实体 id，边 `label` → 关系 id，按 ULTRA 约定加反向边）。这一步写成独立的小函数，方便单独测试。
   - **给已有边打分**：对每条边 `(h, r, t)`，查询 `(h, r, ?)`，记录 `t` 的分数与排名；排名越靠后越可疑。输出 `edge_scores.parquet`（src, label, dst, key, score, rank）。
   - **补缺失边**：对每个 `(h, r)` 取 top-k 中图里不存在的 `t`，输出 `missing_candidates.parquet`（src, label, dst, score）。
   - `units.jsonl`：排名最差的若干条边写成 `finding`（「可疑边」），分数最高的若干缺失候选写成 `finding`（「可能缺失的边」）；`run.json` 按 6.3。
3. smoke test（`tests/test_tools.py` 里）：
   - 图转三元组的函数：用一个十几个节点、两三种关系的小图测实体 / 关系编号与反向边数量（不需要 torch）。
   - 端到端：在同一个小图上跑 `run.py`，检查输出文件齐全、行数与边数一致。ULTRA 依赖不可用时 `pytest.skip`。

## 8. 步骤 7：TabPFN 工具（`tools/tabpfn`）

TabPFN（Prior Labs，`pip install tabpfn`）：表格基础模型，一次前向完成预测。

1. 新建环境 `knosis-tabpfn`，`pip install tabpfn`。首次运行会下载模型权重；**部分版本的权重需要在 HuggingFace 接受许可，且可能不允许商用 —— 在 TOOL.md 的 `license` 里如实写清**（实现者需查当前版本的条款）。提供 `--model` 参数选择版本。
2. `run.py` 两个子命令：
   - `predict --train data/train.parquet --test data/test_features.parquet --target <列> --out <dir>`：输出 `predictions.parquet`（row_id, prediction, 分类时各类概率）与每行不确定性（分类用熵，回归用分位数区间宽度）。
   - `oof --train data/train.parquet --target <列> --out <dir> [--folds 5]`：训练集上的 K 折 out-of-fold 预测；输出每行「真实标签的预测概率」（回归为残差）—— **用来发现可疑标签（标签噪声）**；最可疑的若干行写成 `finding`。
3. 训练行数或特征数超过模型上限时，随机下采样到上限（固定随机种子），在 `run.json` 里记录。
4. 验收：在 `tabarena-houses` 工作区上两个子命令都跑通。
